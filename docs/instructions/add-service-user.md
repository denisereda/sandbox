# Создание сервисного пользователя

Создание отдельного пользователя `backend` / `frontend`  — это ключевой шаг к безопасности вашего сервиса. Идея в том, чтобы запускать приложение с минимально необходимыми правами, а не от имени `root`. Если в приложении обнаружится уязвимость, злоумышленник получит доступ только к ограниченному набору файлов и не сможет навредить всей системе.

Вот пошаговое руководство, как это сделать правильно.

## 🧑‍💻 Шаг 1: Создание системного пользователя

Для сервисов рекомендуется создавать не обычного пользователя, а **системный аккаунт**. У такого аккаунта нет пароля, и он не предназначен для интерактивного входа в систему, что снижает поверхность атаки.

Выполните следующую команду:

```bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin appuser
```

Разберем флаги:

* **`--system`**: Создает системный аккаунт. У таких пользователей UID обычно меньше 1000, и система относится к ним иначе, чем к обычным пользователям.
* **`--no-create-home`** (или `-M`): Не создает домашнюю директорию. Для сервиса она обычно не нужна, а ее отсутствие — это дополнительная мера безопасности.
* **`--shell /usr/sbin/nologin`** (или `-s /sbin/nologin`): Устанавливает оболочку `nologin`, которая немедленно завершает сеанс. Это гарантирует, что даже при компрометации учетных данных войти в систему под этим пользователем не получится.

## 📂 Шаг 2: Настройка прав на директории

Теперь, когда пользователь создан, нужно дать ему права на те директории, с которыми будет работать ваше приложение (например, `/opt/myapp`), и **запретить** доступ ко всему остальному.

Предположим, ваше приложение находится в `/opt/myapp`.

1. **Смените владельца директории приложения:**

    ```bash
    sudo chown -R appuser:appuser /opt/myapp
    ```

    Это делает `appuser` владельцем всех файлов и поддиректорий внутри `/opt/myapp`.

2. **Установите строгие права доступа:**
    Рекомендуется ограничить права так, чтобы только владелец (`appuser`) мог читать и исполнять файлы, а другие пользователи не имели доступа.

    ```bash
    # Устанавливаем права 750 на директории (rwxr-x---)
    sudo find /opt/myapp -type d -exec chmod 750 {} \;

    # Устанавливаем права 640 на обычные файлы (rw-r-----)
    sudo find /opt/myapp -type f -exec chmod 640 {} \;

    # Если есть исполняемые файлы (например, сам бинарник), даем им права на выполнение
    sudo chmod 750 /opt/myapp/myapp
    ```

    **Что это дает:**
    * **`750` для директорий**: Владелец может читать, писать и заходить в директорию. Группа может читать и заходить. Остальные — не могут ничего.
    * **`640` для файлов**: Владелец может читать и писать. Группа может только читать. Остальные — не могут ничего.

3. **Настройте права на директории для логов и данных (если нужны):**
    Если вашему приложению нужно писать логи или данные в отдельные директории (например, `/var/log/myapp` или `/var/lib/myapp`), их тоже нужно сделать доступными для записи пользователю `appuser`.

    ```bash
    sudo mkdir -p /var/log/myapp
    sudo chown -R appuser:appuser /var/log/myapp
    sudo chmod 750 /var/log/myapp
    ```

    Без этого сервис не сможет писать логи, и вы увидите ошибку `Permission denied`.

### 🔗 Шаг 3: Связка с systemd

Теперь, когда пользователь и права настроены, ваш systemd-юнит, который мы обсуждали ранее, будет работать корректно. В нем уже указаны нужные директивы:

```ini
[Service]
User=appuser
Group=appuser
# ... остальные настройки
```

`systemd` запустит процесс от имени `appuser`, и у него будут ровно те права, которые вы определили на шаге 2.
