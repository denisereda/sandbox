# 🔐 Подключение к VM по SSH-ключам: полная инструкция

## Введение: принцип работы

Подключение по SSH-ключам основано на **асимметричном шифровании**. Используется пара математически связанных ключей:

- **Приватный ключ** (например, `id_ed25519`) — хранится только на вашем локальном компьютере и никогда не передаётся на сервер. Это ваш секрет.
- **Публичный ключ** (например, `id_ed25519.pub`) — можно свободно распространять. Он помещается на удалённую VM в файл `~/.ssh/authorized_keys`.

При подключении сервер, зная ваш публичный ключ, отправляет клиенту случайное испытание (challenge). Клиент отвечает на него, используя **приватный ключ** для расшифровки запроса и шифрования ответа. Если ответ верен, сервер убеждается, что у клиента действительно есть соответствующий приватный ключ, и предоставляет доступ. Пароль при этом не передаётся.

## 📝 Пошаговая настройка

### 1. Генерация пары ключей с явным именем

```bash
ssh-keygen -t ed25519 -C "your_email@example.com" -f ~/.ssh/id_ed25519_vm1
```

Где:

- `-t ed25519` — современный и безопасный тип ключа;
- `-C "..."` — необязательный комментарий для идентификации ключа;
- `-f ~/.ssh/id_ed25519_vm1` — **явно задаёт имя приватного ключа**. Публичный ключ будет создан как `~/.ssh/id_ed25519_vm1.pub`.

В результате появятся два файла:

```text
~/.ssh/id_ed25519_vm1
~/.ssh/id_ed25519_vm1.pub
```

При генерации ключа для пользовательского подключения рекомендуется задать **кодовую фразу (passphrase)** — дополнительный пароль для приватного ключа. Если файл с таким именем уже существует, `ssh-keygen` спросит, перезаписывать ли его.

> Если не указывать `-f`, используется путь по умолчанию: `~/.ssh/id_ed25519` и `~/.ssh/id_ed25519.pub`.  
> Если указать только имя без пути, например `-f my_vm_key`, ключи сохранятся в текущей директории.

#### ⚠️ Примечание для CI/CD

Если ключ будет использоваться в системах CI/CD (GitLab CI, GitHub Actions, Jenkins и т.п.), **ключ нужно создавать без passphrase**. В автоматическом режиме нет человека, который введёт кодовую фразу, поэтому ключ с passphrase в CI работать не будет.

Для генерации ключа без passphrase используйте параметр `-N ""` (либо просто не вводите passphrase):

```bash
ssh-keygen -t ed25519 -C "ci-key@project" -f ~/.ssh/id_ed25519_ci -N ""
```

Где:

- `-f ~/.ssh/id_ed25519_ci` — явное имя пары ключей;
- `-N ""` — пустая passphrase, то есть ключ создаётся без кодовой фразы.

В результате появятся:

```text
~/.ssh/id_ed25519_ci
~/.ssh/id_ed25519_ci.pub
```

**Важно:**

- Приватный ключ без passphrase — это фактически «пароль» к серверу. Его нельзя коммитить в репозиторий, отправлять в чаты или хранить в открытом виде.
- В CI приватный ключ нужно хранить только в **защищённых секретах** (GitLab CI Variables, GitHub Actions Secrets, Jenkins Credentials и т.д.).
- Лучше использовать **отдельный ключ только для CI**, а не личный ключ разработчика.
- Для CI-ключа стоит ограничить права на сервере: отдельный пользователь, `authorized_keys` с ограничениями (`command=`, `from=`, `no-pty` и т.п.), минимально необходимые права.
- Периодически ротируйте CI-ключи и отзывайте старые.

Если ключ создаётся для ручного подключения разработчика, passphrase, наоборот, **рекомендуется** задавать.

### 2. Копирование публичного ключа на VM

Скопируйте именно публичный ключ с заданным именем:

```bash
ssh-copy-id -i ~/.ssh/id_ed25519_vm1.pub username@server_ip
```

Ручной вариант:

```bash
cat ~/.ssh/id_ed25519_vm1.pub
```

и добавьте содержимое в `~/.ssh/authorized_keys` на сервере.

### 3. Права доступа

SSH строг к правам. На сервере выполните:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

На локальной машине желательно ограничить доступ к приватному ключу:

```bash
chmod 600 ~/.ssh/id_ed25519_vm1
```

### 4. Подключение с явно заданным ключом

Если имя ключа нестандартное, укажите его через `-i`:

```bash
ssh -i ~/.ssh/id_ed25519_vm1 username@server_ip
```

Если используется имя по умолчанию `~/.ssh/id_ed25519`, флаг `-i` обычно не нужен.

Для CI вместо `ssh-agent` приватный ключ обычно передаётся в шаг пайплайна из секрета и используется так:

```bash
ssh -i "$CI_SSH_PRIVATE_KEY_FILE" username@server_ip
```

### 5. Дополнительно: `ssh-agent`

Чтобы не вводить кодовую фразу каждый раз при ручном подключении, добавьте ключ в `ssh-agent`:

```bash
ssh-add ~/.ssh/id_ed25519_vm1
```

## 💡 Дополнительные рекомендации

- **Никогда не передавайте приватный ключ.** Публичный ключ, наоборот, предназначен для распространения.
- **Облачные провайдеры** (AWS, Azure, Google Cloud) позволяют указать публичный ключ при создании VM. В этом случае провайдер сам добавит его в `authorized_keys`.
- **Запрет парольного входа** на сервере: после успешной настройки ключей в `/etc/ssh/sshd_config` установите `PasswordAuthentication no` и перезапустите `sshd`. Это заметно повышает безопасность.
- **Ротация ключей**: периодически меняйте ключи и удаляйте устаревшие строки из `~/.ssh/authorized_keys`.
