# Сквозное практическое задание

## Начальные требования

1. УЗ GitLab.
2. УЗ Yandex ID.
3. Регистрация и первый вход YC, с настройкой платежного средства.
4. Установка Docker (deocker desktop / docker engine).
5. Установка Git.
6. Установка VSCode и расширений (Docker, Git Graph, YAML, markdownlint, Container Tools, Dev Containers).

1. Проверить наличие и работоспособность Docker.
2. Поставить наличие VSCode.

5. Создать репозиторий sandbox.

8. Клонировать репозиторий на локальную машину.  
9. Расположить в него необходимые файлы DevContainers (используя базовые команды терминала).
10. Поставить DevContainers, запустить DevContainers, проверить работу утилит, остановить DevContainers.

1. Собрать решение в Docker локально.

3. Запустить сервисы в docker compose.

## Локальная сборка и запуск решения в docker

Для создания Dockerfile используйте наработки с прошлого урока.

Ваши файлы должны быть созданы с использование подхода multistage: стадия `builder` - для сборки, стадия `runtime` - для запуска приложения.

Для запуска приложения backend используйте тот же образ, что и для сборки.

Для запуска приложения frontend используйте образ node с установленным web-сервером `http-server`.

Запускайте процесс через отдельные sh-скрипты (по одному файлу на каждый из компонентов системы). Назовите их: `biild-docker.sh`. Скрипты сборки с предыдущего урока, которые производят сборку и отправку артефактов на `nexus` переименуйте в `build-raw.sh`.

## Запуск решения в docker compose (без сборки)

При создании конфигурации docker compose:

1. Создайте выделенную сеть для вашего приложения.
2. Не используйте стадию сборки (ваш docker-compose.yml будете использоваться для развертывания приложения, поэтому стадия сборки не будет уместна).
3. Используйте тег `latest` для первичной проверки.
4. Подключите файл с переменными окружения к конфигурации и пробросьте все необходимые параметры и секреты через переменные окружения (`env_file`).

При тестировании вы должны получить возможность использования браузера на локальном хосте для полноценного запуска приложения и проверки его на работоспособность.

## Развертывание решения вручную в docker compose на VM (теги latest)

1. Перед развертыванием решения установите все необходимые компоненты экосистемы docker на VM.
2. Для развертывания напишите скрипт, который можно будет исполнить на удаленной машине или можно будет запустить построчно при подключении с помощью `ssh`.
3. Для запуска вам придется стянуть нужные образы, это можно сделать вручную, выполнив необходимые команды.

> Если для доступа к Nexus используется протокол http, то придется прописать адрес хоста Nexus в /etc/docker/docker.json в качестве insecure-registries.

## Создание пайплайна развертывания (используя docker compose и последнюю версию образа)

1. Пайплайн развертывания необходимо в виде bash-скрипта, он должен обеспечивать автоматизированное развертывание.
2. Пайплайн должен содержать один шаг, требующий интерактивного ввода секретных данных - шаг `docker login`.
3. Убедитесь, что ваш скрипт запуска учтет все изменения, внесенные в docker-compose.yml и применит их при повторном запуске пайпайна.
4. Убедитесь, что ваш скрипт учитывает изменения образа на удаленном registry даже в случае использования идентичного тега (например `latest`).

## Этап 3: Github actions

1. Подготовить секреты и окружение GitHub для сборки и деплоя.
2. Реализовать пайплайн сборки приложения с публикацией образов в два registry (ghcr.io и Nexus) и сквозным версионированием.
3. Реализовать пайплайн развертывания приложения с использованием docker compose (ssh/scp).
4. Опционально: настроить ограничения и параллелизм пайплайна (`permissions`, `concurrency`).
5. *Добавить прогон модульных тестов (если они имеются в сервисах).

### Подготовка окружения

1. Убедитесь, что в репозитории на GitHub есть директория `.github/workflows/` — именно в ней GitHub ищет описания пайплайнов.
2. Создайте отдельную SSH-пару для деплоя, публичную часть добавьте в `~/.ssh/authorized_keys` на VM. Не используйте свой личный ключ.
3. В **Settings → Secrets and variables → Actions** добавьте секреты:
   - `VM_HOST`, `VM_USER` — адрес и пользователь VM в YC;
   - `VM_SSH_KEY` — приватный ключ деплоя;
   - `VM_SSH_KNOWN_HOSTS` — вывод `ssh-keyscan <VM_HOST>`;
   - `NEXUS_HOST`, `NEXUS_REPO_USER`, `NEXUS_REPO_PASS` — доступ к Nexus;
   - `GHCR_PAT` — токен со scope `read:packages` для `docker login` на VM.
4. В **Settings → Environments** создайте окружение `production`; при желании включите **Required reviewers**, чтобы деплой требовал подтверждения.
5. Проверьте, что security group VM в YC разрешает входящий SSH (порт 22) — иначе раннер не сможет подключиться.

> Секреты не должны попадать в репозиторий и в логи пайплайна. Не включайте `set -x` в скриптах деплоя.

### Триггеры и структура пайплайна

1. Пайплайн запускается при пуше в любую ветку и вручную:

   ```yaml
   on:
     push:
       branches: ["**"]
     workflow_dispatch:
   ```

   Обработка форков и `pull_request` не требуется.

2. Пайплайн описывается одним файлом `.github/workflows/ci.yml` с тремя job'ами:

   ```text
   version → build → deploy
   ```

3. `deploy` выполняется при пуше в любую ветку, а также при `workflow_dispatch` для повторного деплоя/отката:

   ```yaml
   if: github.ref_type == 'branch' || github.event_name == 'workflow_dispatch'
   needs: [version, test, build-ghcr]
   ```

   Все ветки деплоятся в один каталог `/opt/sandbox` и на один порт `8889`, поэтому побеждает последний запуск.

4. Ручной запуск (`workflow_dispatch`) принимает входной параметр `VERSION` — для повторного деплоя и отката.

### Требования к именованию образов

1. Имена — только lowercase, в kebab-case, без пробелов и подчёркиваний.
2. Компоненты называются `backend` и `frontend`; имя образа — `sandbox-<component>`.
3. В Nexus образ размещается в **личном hosted-репозитории** `<фамилия>-docker`:
   - `<NEXUS_HOST>/<фамилия>-docker/sandbox-backend:<tag>`;
   - `<NEXUS_HOST>/<фамилия>-docker/sandbox-frontend:<tag>`.
4. В ghcr.io вместо личного репозитория Nexus используется пространство имён владельца:
   - `ghcr.io/<owner>/sandbox-backend:<tag>`;
   - `ghcr.io/<owner>/sandbox-frontend:<tag>`.
5. Полные наименования образов и registry необходимо передать через `.env` (`BACKEND_IMAGE`, `FRONTEND_IMAGE`, `REGISTRY`), чтобы `docker-compose.yml` не зависел от конкретного registry.

### Требования к версионированию

1. Версия вычисляется один раз за запуск пайплайна в UTC:

   ```sh
   VERSION=$(date -u +%Y%m%d-%H%M%S)
   ```

   Пример: `20261111-101500`.

2. Каждый образ получает теги:
   - `$VERSION` — всегда (неизменяемый, для деплоя и отката);
   - `sha-<7 символов SHA коммита>` — всегда (трассировка до коммита);
   - `latest` — **только для пуша в основную ветку** (`main`). Из feature-веток `latest` не публикуется, иначе последняя сборка любой ветки перезапишет стабильный тег.

3. Один образ собирается один раз и пушится в оба registry (не собирайте отдельно под каждый registry).
4. `VERSION` передаётся из job'а `version` в `build` и `deploy` через `outputs`, чтобы теги в ghcr.io и Nexus совпадали.
5. `VERSION` никогда не переиспользуется: повторная сборка того же коммита = новый timestamp.
6. Откат выполняется указанием предыдущего `VERSION` — пересборка не нужна.

### Пайплайн сборки (job `build`)

1. Job `version` вычисляет версию и отдаёт её дальше:

   ```yaml
   - run: echo "version=$(date -u +%Y%m%d-%H%M%S)" >> $GITHUB_OUTPUT
     id: version
   ```

2. Job `build` использует матрицу по компонентам (`backend`, `frontend`), чтобы не дублировать шаги. Внутри — только явные команды Docker, без специализированных actions:
   - `actions/checkout`;
   - шаг `Allow HTTP access to Nexus`: Nexus доступен по http, поэтому его хост прописывается в `/etc/docker/daemon.json` в `insecure-registries`, после чего демон перезапускается. Это единственное место настройки: тот же демон используется для `docker login`, `docker build` и `docker push`, отдельная настройка BuildKit не нужна;
   - `docker login` дважды — в `ghcr.io` (по `GITHUB_TOKEN`) и в Nexus (по `NEXUS_REPO_USER`/`NEXUS_REPO_PASS`), пароль передаётся через `--password-stdin`;
   - `docker build` собирает образ **один раз** и проставляет теги сразу для **обоих registry**:

     ```bash
     docker build \
       --tag "${GHCR_IMAGE}:${VERSION}" \
       --tag "${GHCR_IMAGE}:sha-${SHORT_SHA}" \
       --tag "${NEXUS_IMAGE}:${VERSION}" \
       --tag "${NEXUS_IMAGE}:sha-${SHORT_SHA}" \
       "./src/${COMPONENT}"
     ```

   - `latest` добавляется только для основной ветки:

     ```bash
     if [ "${GITHUB_REF}" = "refs/heads/main" ]; then
       TAGS+=(--tag "${GHCR_IMAGE}:latest" --tag "${NEXUS_IMAGE}:latest")
     fi
     ```

   - Имена registry задаются в `env` job'а:

     ```yaml
     GHCR_IMAGE: ghcr.io/${{ github.repository_owner }}/sandbox-${{ matrix.component }}
     NEXUS_IMAGE: ${{ secrets.NEXUS_HOST }}/sereda-${{ matrix.component }}-docker/sandbox-${{ matrix.component }}
     ```

     > `sereda` замените на свою фамилию.

   - `docker push --all-tags` отправляет собранный образ в оба registry:

     ```bash
     docker push --all-tags "${GHCR_IMAGE}"
     docker push --all-tags "${NEXUS_IMAGE}"
     ```

4. Проверка результата: образы видны в **Packages** и в Nexus, локально выполняется `docker pull ghcr.io/<owner>/sandbox-backend:latest`. После пуша в feature-ветку появились `$VERSION` и `sha-*`, а `latest` не изменился; после пуша в `main` обновился и `latest`.

### Пайплайн развертывания (job `deploy`)

1. Job выполняется после `build` при пуше в любую ветку, плюс `workflow_dispatch` для повторного деплоя/отката.
2. Образы всегда скачиваются из ghcr.io: `ghcr.io/<owner>/sandbox-backend` и `ghcr.io/<owner>/sandbox-frontend`.
3. Шаги деплоя «голым» ssh/scp:
   - `actions/checkout`;
   - сформировать `.env` из трёх переменных: `REPOSITORY_BACKEND`, `REPOSITORY_FRONTEND`, `IMAGE_TAG=$VERSION`;
   - `scp` на VM: `docker-compose.yml`, `.env`, `deploy-docker-compose-ci.sh`;
   - по `ssh`: `docker login ghcr.io`, `docker compose pull`, `docker compose up -d --remove-orphans --force-recreate`, `docker image prune -f`;
   - `curl` по health-эндпоинту; если проверка не прошла — пайплайн падает.
4. Для деплоя нужны секреты `VM_HOST`, `VM_USER`, `VM_SSH_KEY`, `VM_SSH_KNOWN_HOSTS` и встроенный `GITHUB_TOKEN` с правом `packages: read`.
5. Обновление `latest`: `docker compose pull` всегда забирает новый digest, `up -d` пересоздаёт контейнер при его изменении; если контейнер не обновился — добавьте `--force-recreate`.
6. Секреты используйте только в шагах деплоя и не выводите в лог.
7. Откат: запустите деплой вручную с `VERSION` предыдущей сборки — compose подтянет неизменяемый тег.

### Опциональные настройки пайплайна

1. Явно ограничьте права токена:

   ```yaml
   permissions:
     contents: read
     packages: write
   ```

   > Если в настройках репозитория `GITHUB_TOKEN` уже имеет доступ к пакетам, блок можно опустить. При ограниченных правах по умолчанию без `packages: write` пуш в ghcr.io не пройдёт.

2. Для сборки задайте отмену устаревших запусков одной ветки:

   ```yaml
   concurrency:
     group: build-${{ github.ref }}
     cancel-in-progress: true
   ```

3. Для деплоя запретите параллельные запуски:

   ```yaml
   concurrency:
     group: deploy-production
     cancel-in-progress: false
   ```

4. Проверьте поведение: два пуша подряд в одну ветку отменяют предыдущую сборку, а повторный запуск деплоя дожидается завершения текущего.

### Модульные тесты (*)

1. Добавьте job `test`, выполняемый до сборки; `build` и `deploy` зависят от него через `needs`.
2. Запускайте тесты в контейнере из стадии `builder`: `npm ci && npm test` или `mvn test` — окружение совпадает с локальным.
3. Публикуйте отчёты (JUnit, coverage) через `actions/upload-artifact`.
4. Включите job `test` в **Branch protection → Require status checks**.

### Дополнительные доработки (*)

1. Максимально упростите скрипты, чтобы использовалась только понятная вам логика.
2. По возможности уберите лишние опции.
3. По возможности уберите лишние actions.

## Этап 4: Пробуем kubernetes, helm

1. Разверните кластер managed k8s cluster Yandex Cloud.
2. Установите и настройте утилиту yc.
3. Установите `kubectl` и настройте для использования с вашим кластером.
4. Создайте нативные манифесты k8s для backend и frontend и задеплойте их его с помощью `kubectl`. Обратите внимание, что для frontend вам обязательно понадобится `service`, `NodePort`. Для проверки используйте команду: `kubectl exec -it -n default deployment/sandbox-backend -- /bin/sh`.
5. Удалите приложение перед использование конфигурации для helm.
6. Установите и настройте `helm`. Проверка соединения с кластером: `helm list`
7. Создайте простейший манифест с параметризацией параметров потребления сервисов, а так же версии. Версию мы будем передавать в тексте команды `helm update` (`helm template` для проверки).
8. Задеплойте свой первый релиз c помощью `helm`.
9. Откатите релиз с помощью команды `rollback` с версии 2 на версию 1.
10. Реализуйте отдельный пайплайн развертывания `cd.yml`, позволяющий сделать развертывание вручную, с указанием версии. В пайплайне CI (`ci.yml`) оставьте этапы версионирования, тестирования и сборки. `kube-config` сформируйте на агенте при помощи утилиты `yc`, предварительно настройте утилиту при помощи команды `yc init`, в качестве входных параметров конфига используйте авторизованный ключ для сервисного аккаунта, создайте его при помощи web-консоли YC, сохранив в секрет с именем `YC_SA_KEY`.

## Этап 5: Доработки

1. Установите ingress-контроллер в свой кластер (см. официальную документацию от Yandex).
2. Создайте конфигурацию для ingress для нашего приложения (вам потребуется собственный домен, делегирование домена на Yandex Cloud DNS, самоподписанный сертификат LetsEncript или настройка cert-manager).
3. Включите опцию поддержки сохранения заказов в СУБД, разверните СУБД и настройте накатку миграций.
4. Опишите развертывание вашего кластера / VM в terraform.
5. Оптимизируйте код Dockerfile для ваших образов согласно лучшим практикам: минимум слоев, слои от редко-меняющихся к часто-меняющимся.
